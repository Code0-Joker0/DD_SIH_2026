SIH 2026 Architecture Runbook
==============================

This runbook starts the current local architecture without changing ~/.bashrc,
/etc files, Docker installation, or other system configuration. Commands that
say `source` or `export` affect only the current terminal session.

Current profiles:
- Local GPU: RTX 5070, approximately 12 GB VRAM, Qwen2.5-Coder 7B AWQ.
- A100: Qwen3-Coder 30B AWQ with a 32K context window.

The local profile stores runtime data under `/home/ved/.cache/sih_2026`; it does
not require a `/data` directory or sudo.
Because the local RTX 5070 is reserved for the 7B vLLM model, BGE-M3 and the
reranker default to CPU. The A100 profile can set `BGE_DEVICE=cuda` and
`RERANKER_DEVICE=cuda` if GPU memory permits.

1. Check host prerequisites
---------------------------
Run these from the repository root:

    cd /home/ved/Coding/SIH_2026
    nvidia-smi
    uv --version
    docker --version
    docker compose version
    git --version

If `uv` is missing, do not run the installer automatically. Install it using
your approved local method, or ask an administrator. Do not append anything to
`~/.bashrc`.

Docker Engine must be running and the current user must have access to
`/var/run/docker.sock`. If Docker is unavailable, ask the system administrator
to start/configure it. Do not install Docker, run apt, or change Docker group
membership as part of this project runbook.

Docker startup troubleshooting
-------------------------------
If `systemctl start docker` reports `start-limit-hit`, that is only systemd
throttling repeated failures. Inspect the first daemon error before retrying:

    sudo systemctl status docker.service --no-pager -l
    sudo journalctl -u docker.service -n 100 --no-pager
    sudo systemctl status containerd.service --no-pager -l

For the current failure, the important message is an iptables/nftables error
about Docker being unable to append to the `nat-PREROUTING` chain. UFW is active
on this host, so an administrator should inspect the firewall state:

    sudo ufw status verbose
    sudo iptables --version
    sudo iptables -t nat -S
    sudo nft list ruleset

Do not flush firewall rules or switch between `iptables-nft` and
`iptables-legacy` without understanding the host firewall policy. Those are
host-level changes and can remove networking protections. After the cause is
resolved by the administrator, clear systemd's failure counter and retry:

    sudo systemctl reset-failed docker.service docker.socket
    sudo systemctl start docker.service
    docker info

If `docker info` says permission denied, the user is not in the current shell's
docker group yet. Activate the already-configured group for this shell with:

    newgrp docker

This starts a subshell only; it does not edit `~/.bashrc`. Alternatively, log
out and back in. Verify with `id` and then rerun `docker info`.

2. Select the machine profile
-----------------------------
The repository contains both profiles. Use the development profile on the
local GPU:

    ln -sfn .env.dev .env

Use the server profile on the A100:

    ln -sfn .env.server .env

Load the profile for this terminal only and create runtime directories:

    set -a
    source .env
    set +a
    mkdir -p "$HF_HOME" "$QDRANT_STORAGE" "$LOG_DIR"

Never commit `.env`, `.env.dev`, or `.env.server`. Keep secrets such as
`HF_TOKEN` outside tracked files. A Hugging Face token may be exported in the
current shell when needed:

    export HF_TOKEN='your-token'

3. Create or refresh the API environment
----------------------------------------
The virtual environment is local to the repository and does not modify the
system Python:

    cd apps/api
    uv venv --python 3.11 --seed
    source .venv/bin/activate
    uv pip install --constraint ../../constraints.txt \
      qdrant-client sentence-transformers numpy python-dotenv pypdf
    uv pip install --constraint ../../constraints.txt vllm --torch-backend=auto
    cd ../..

Run this again on a different machine. Do not copy `.venv` between machines;
recreate it so packages match the new CPU/GPU environment.

Verify the installation:

    source apps/api/.venv/bin/activate
    python -c "import torch; print(torch.__version__, torch.version.cuda, torch.cuda.is_available())"
    python -c "import vllm; print(vllm.__version__)"
    python -c "import torch, vllm, qdrant_client, sentence_transformers; print('imports OK')"

The vLLM launcher automatically exposes the CUDA compiler packaged in the
project venv for FlashInfer JIT compilation. Do not edit `.venv/bin/activate`
or any shell startup file. If you run vLLM manually, use a session-only export:

    export CUDA_HOME="$PWD/apps/api/.venv/lib/python3.11/site-packages/nvidia/cu13"
    export PATH="$CUDA_HOME/bin:$PATH"

The launcher also creates user-owned compatibility links for the packaged
toolkit's `lib/` layout (`lib64` and `libcudart.so`) when they are absent.

This host uses GCC 16, but GCC 15 is installed and the launcher uses
`/usr/bin/g++-15` for CUDA compilation without changing the system default. If
GCC 15 is unavailable, it falls back to `-allow-unsupported-compiler`. The
packaged nvcc is 13.3 while the runtime headers are 13.2, so the launcher also
disables FlashInfer's strict CCCL version check for this child process. A
matching GCC/CUDA toolkit pair is preferable for production.

Pressing `Ctrl-C` during startup now stops the background vLLM child as well;
it does not leave a model process consuming GPU memory.

4. Start Qdrant
---------------
First validate the Compose file:

    docker compose --env-file .env \
      -f infrastructure/docker/docker-compose.yml config --quiet

Start Qdrant:

    ./scripts/qdrant_up.sh

Check it:

    curl -s http://localhost:${QDRANT_PORT}/collections

Stop it when finished:

    ./scripts/qdrant_down.sh

Qdrant data is stored in `$QDRANT_STORAGE`, outside the repository. Back up
that directory before moving machines.

5. Start the vLLM server
------------------------
This downloads the selected model on first use and reserves GPU memory. Start
it only when the GPU is available:

    ./scripts/vllm_up.sh

Check it:

    curl -s http://localhost:${VLLM_PORT}/v1/models
    curl -sf http://localhost:${VLLM_PORT}/health

Stop it to release GPU memory:

    ./scripts/vllm_down.sh

The server log and PID file are written under `$LOG_DIR`. If startup reports a
DeepGEMM/CUDA_HOME warning, keep `VLLM_USE_DEEP_GEMM=0` in the selected profile
and do not modify system files.
Each launcher attempt starts a fresh `vllm.log`, so a failure can be diagnosed
without mixing traces from older model processes.

Run `vllm_up.sh` as the normal project user, never with `sudo`. The script uses
`apps/api/.venv/bin/vllm` directly, creates user-owned logs, and refuses to kill
an unrelated process when stopping. If an earlier `sudo` run created root-owned
files, an administrator must repair ownership once, for example:

    sudo chown -R "$USER":"$(id -gn)" "$LOG_DIR"
    sudo chown -R "$USER":"$(id -gn)" "$HF_HOME"

Do not use `sudo chmod +x` for this script; executable permissions belong to
the repository and are already set by `chmod +x scripts/*.sh`.

6. Start both services or inspect status
----------------------------------------
Once Docker is available and the profile is loaded:

    ./scripts/dev.sh up
    ./scripts/dev.sh status

Stop both services in the correct order:

    ./scripts/dev.sh down

The FastAPI health and document chunking endpoints are implemented. Start that
slice separately with:

    PYTHONPATH=apps/api uvicorn app.main:app --host 127.0.0.1 --port 8080
    curl http://localhost:8080/health

Agent orchestration and frontend modules remain placeholders. The RAG path is
implemented under `app/rag/`; ingestion supports TXT, PDF, and DOCX through
`scripts/ingest_documents.py`.
`scripts/create_collection.py` and `scripts/health_check.py` require a running
Qdrant.

8. Stop and verify the black-box state
---------------------------------------
To release project resources:

    ./scripts/vllm_down.sh
    ./scripts/qdrant_down.sh

Then verify that no project process or port remains:

    pgrep -a -f 'vllm|qdrant' || true
    ss -ltnp | grep -E ':(6333|6334|8000|8080)\\b' || true
    docker ps
    nvidia-smi

An empty result for the first two checks means the project processes and ports
are stopped. `docker.service`, `containerd`, and the Docker socket may remain
running as host services; stop those separately only when the whole machine no
longer needs Docker. The Qdrant data remains on disk by design.

For the security boundary, verify UFW is enabled and the service ports are
loopback-only:

    sudo ufw status verbose
    ss -ltnp | grep -E ':(6333|6334|8000|8080)\\b' || true

The Compose file publishes Qdrant only on `127.0.0.1`, so it is not reachable
from the network. The vLLM launcher likewise binds to `127.0.0.1` by default;
do not set `VLLM_HOST=0.0.0.0` unless a separate authenticated reverse proxy is
deliberately configured. Docker socket access is effectively root-equivalent; keep the
`docker` group limited to trusted users. Do not treat a running Docker daemon
as a stopped/black-box state: it is a host-level service, not an application
resource. Qdrant's bind-mounted storage may remain `root:root` because the
container writes it as root; do not delete it during shutdown because it holds
the database state.

9. Moving from the local GPU to the A100
----------------------------------------
Before shutting down the old machine:

    ./scripts/dev.sh down

Back up or copy these project/runtime items:
- The repository and committed configuration.
- `$QDRANT_STORAGE` for the Qdrant collection data.
- `$HF_HOME` if you want to avoid downloading models again.
- `$LOG_DIR` if logs are needed for troubleshooting.

On the A100 machine:

    git clone <repository-url>
    cd SIH_2026
    ln -sfn .env.server .env
    set -a
    source .env
    set +a
    mkdir -p "$HF_HOME" "$QDRANT_STORAGE" "$LOG_DIR"

The A100 profile explicitly sets `BGE_DEVICE=cuda` and
`RERANKER_DEVICE=cuda`, so both BGE-M3 and `bge-reranker-v2-m3` load on the
GPU. Verify the device before ingesting or querying:

    python -c "import torch; print(torch.cuda.get_device_name(0)); print(torch.cuda.is_available())"
    python -c "from app.core.config import EMBEDDING_DEVICE, RERANKER_DEVICE; print(EMBEDDING_DEVICE, RERANKER_DEVICE)"

Keep vLLM's GPU memory setting below the A100 capacity and monitor memory while
loading all three models. If the combined footprint is too high, lower
`VLLM_GPU_MEM_UTIL` or temporarily set one component's device to `cpu`; do not
silently change the profile.

Copy the saved Qdrant storage and optional Hugging Face cache into the paths
above, preserving ownership and permissions. Recreate the Python environment
using section 3; do not copy `.venv` from the local GPU.

Then verify the A100 and start services:

    nvidia-smi
    source apps/api/.venv/bin/activate
    python -c "import torch; print(torch.cuda.is_available())"
    docker compose --env-file .env \
      -f infrastructure/docker/docker-compose.yml config --quiet
    ./scripts/dev.sh up
    ./scripts/dev.sh status

The profile changes the model and context length only:
- Local GPU: `Qwen/Qwen2.5-Coder-7B-Instruct-AWQ`, `8192` tokens.
- A100: `Qwen/Qwen3-Coder-30B-A3B-Instruct`, `32768` tokens.

10. Commands deliberately excluded
----------------------------------
Do not run these automatically:
- `curl ... | sh` installers.
- `sudo apt ...` or other system package installation.
- `sudo usermod -aG docker ...`.
- Edits to `~/.bashrc`, `/etc/*`, or `.venv/bin/activate`.
- Starting vLLM when the GPU is needed by another process.
- `git clone <YOUR_REPOSITORY_URL>` from inside an existing checkout.
